# Generator blocks as a library: `@solidjs/blocks`

Status: implemented on `blocks-lib` (cut from `upstream/next` at 644eaf3b). Nine example twins run on it. This document is the reference for what the library is, what it enforces and where, what it costs, and what it cannot do without a blocks compiler.

## 1. What it is

Generator blocks — `$component(function* (props) { setup; return function* () { view } })` — as a userland library on stock Solid 2. Nothing in `@solidjs/signals`, `solid-js` or `@solidjs/web` changes. Three pieces sit outside the runtime package:

| Package                                      | What                                                                                                                                                         | Kind                       |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| `@solidjs/blocks`                            | runtime interpreter, strict types, flow controls, render / hydrate, a settled-only JSX namespace, the no-JSX `h` wrapper, an automatic JSX runtime | userland (public API only) |
| `@solidjs/compiler`, `@solidjs/babel-plugin` | **one syntactic rule** in both JSX transforms (`yield*` inside JSX → `perform(…)`), and `summarizeBlocks` (analysis only, never rewrites)                    | compiler                   |
| `@solidjs/blocks-linker`                     | the type linker: joins what every render site passes into each component's props, writes declaration-merged prop colors; Vite plugin + `solid-link` CLI      | build tool                 |
| `@solidjs/eslint-plugin-blocks`              | nine rules for what TypeScript cannot express                                                                                                               | lint                       |

### Surface

- **Components and blocks**: `$component`, `lazy` (Solid's `lazy()` with the same signature, as a block component: pending while its chunk loads, colored as the loaded component, usable in call form `{yield* Page()}`; D-047 — `adopt` is removed, and a foreign non-lazy component has no bridge). A row (a render callback of `For`, `Repeat`, `Show`, `Match`, an `Errored` fallback) and a no-JSX hole are bare `function*`s; there is no wrapper (`$` and `$scope` are removed, D-013).
- **Rows and components are one shape** (D-030): a row's body is a setup, as a `$component`'s is. It runs once per row (per item, per shown branch), untracked, with the render arguments as reads; it creates (a `yield* $memo` there is the row's, created once per item and disposed with the row) and returns the row's view generator, which only reads. A row that returns its markup directly is a dev error (`ROW_VIEW`), as a setup that returns no view is (`COMPONENT_VIEW`). A derivation several holes read is a `yield* $memo` in the setup or the row's setup; a JSX hole is a `yield*` in JSX; a no-JSX hole is a source, a path or a bare zero-arity `function*` given to `h` or to a flow control's source prop (`Show({ when: function* () { … } })`).
- **Setup operations** (`yield*` in a setup): `$signal`, `$store`, `$memo` (with `loadingValue`: not pending), `$optimistic` (the scalar form, as `$signal`), `$optimisticStore` (the object-or-body form, as `$store`: a value, or a derived body; D-014), `$projection` (a derived store; `seedLoadingValue`: not pending), `$dynamic` (a component from a body: server-component calls), `$effect`, `$settled`, `$cleanup`, `$snapshot`, `yield* Ctx` on a context made with the library's `createContext` — the one way to read a context (D-036: `context(Ctx)` for a foreign context is removed; a foreign context is wrapped once in a library context). A generator helper that creates (`function* createTodos() { … }`) is delegated to with `yield*`, so its creations are the setup's.
- **Reads** (`yield*` anywhere that reads): sources, prop and store paths, `readStore(store, select)`, `latestOf`, `isPendingOf`.
- **Strict**: every read and every write is a `yield*`. Typed failures are complete for library-mediated failures (`raise`, an `attempt`'s handler); a plain `throw` in a block is a bug, surfaced in development as `[UNTYPED_THROW] <host> in <Component>: …` (naming the setup / view / hole / memo / effect / event); like any failure it goes to the nearest `Errored` if there is one, otherwise it is re-thrown (D-019, D-033 — the library installs no root boundary). A view has no body (D-032): it is `function* () { return <…/>; }`, every read is a hole (a `yield*` in a JSX position; in `h` a source or a bare `function*` hole), and structure comes from flow controls (`<Show>`, `<Match>`, `<For>`, …), which take sources directly — no `yield*` outside JSX, no `if` / early `return`, no local computation. A read at a JSX view's top level is the dev error `READ_IN_VIEW` and a lint error (`no-read-in-view-body`); an `h` view's type refuses any yield (`[HVIEW_READ]`, its only check, D-049 — the runtime cannot tell the flavors apart, so `READ_IN_VIEW` also fires for an `h` view reached through a cast). Flow controls take a source or a bare `function*` hole for `when` / `each` / `count` (D-038; in JSX a settled one). A setter call returns a receipt and writes only when it is delegated to (`yield* setX(v)`), so every write is a `Write` in the block's type and only an `$event` or an `$effect` accepts it; a setter call that is not delegated is a lint error (`no-unyielded-write`) and, in development, `UNYIELDED_WRITE` when its run ends (D-021: every run checks the receipts it minted; an `$event` call checks once its body ends, so a receipt minted before an async `attempt` and delegated to after it is fine); a setter called with no block running — handed to plain code, `onClick={setX}`, a timer — throws `SETTER_OUTSIDE_RUN` at the call (D-028; production keeps the silent no-op). Block code holds no reactive state the library did not create: plain Solid's primitives, the router's reactive hooks and `dynamic` are lint errors (`no-foreign-reactive`), each with its block form. There is no wrapper for foreign accessors or stores (`read`, `paths`) and no way back to a plain accessor (`accessor`).
- **Effects of failure and waiting**: `attempt(fn, onError)`: `onError` (required) turns what `fn` threw, or its promise rejected with, into the error object the block fails with, so every failure has a type, each error class its own color; when `fn` returns a promise a `$memo` / `$event` suspends on it. `raise(error)` fails with a typed error. `until(source, onError, options)` waits for a source to read truthy. `attempt` is the one place a failure gets its type: a `$memo`, `$optimisticStore`, `$projection` or `$dynamic` body that returns a promise or a stream returns it through `attempt` (`return yield* attempt(() => watch(feed), cause => new FeedError(cause))`; returning one raw is a type error). A promise is waited for; a stream (or a promise of one) is given back as itself, its failures going through the handler as they come, by a Proxy that changes only how it fails (a server function's brand, a live source's `onstatus` stay its own). `$dynamic`'s component is a plain one: its failures are not in its type.
- **Events**: `$event(function* (e) {…})` is a Solid `action`: every call is one transaction (writes are held until it settles; an async `attempt` re-enters it; a rejection is thrown at the `yield*`). It takes any arguments and returns a promise of its result, so block code does not need `action`; `yield* refresh(store)` and `yield* until(source)` are its forms of Solid's `refresh` / `until`. A failure goes to whoever handles the returned promise; one nobody handles (a DOM dispatch) goes to the nearest `Errored`. An event has two colors in its type, apart from its failures: `P`, it reads a pending source (and waits for its data), and `A`, it does async work of its own (an async `attempt`, `until`). Calling an event is an operation: `yield* save(x)` waits for the call and joins both its colors and its failures to the caller's type (so they travel through any depth of calls). An `$effect` cannot wait, so it may delegate only to an event with neither color. With type information, `no-unyielded-write` reports an event call a block uses any other way. Setters return receipts (`yield* setX(v)` is a `Write`).
- **Flow and boundaries**: `For`, `Repeat`, `Show`, `Switch`, `Match`, `Loading`, `Errored` — Solid's, typed for blocks, render callbacks may be row blocks; boundaries in tag or call form. Failures are a union of error types, each its own color: `Errored` handles them all, or with `catch={[NotFound, …]}` only those types (its fallback receives them; any other is rethrown to the boundary above, and stays in the type). A tree with an unhandled pending read or failure is not an element, so `render` / `hydrate` refuse it. Every failure type is a `Failure` — an `Error` with a literal `kind` (`readonly kind = "not-found" as const`), checked at `attempt`, `until`, `raise` and `Errored`'s `catch` (D-034): TypeScript removes a handled class structurally while the runtime matches with `instanceof`, so two classes of one shape would be one type; a missing or plain-string `kind` is the type error `[FAILURE_KIND]`.
- **Mounting**: `render`, `hydrate` (a settled root); `@solidjs/blocks/jsx-runtime`.
- **No-JSX**: `@solidjs/blocks/h` — the `h` flavor (D-012 as amended by D-046: `html`` ` tagged templates are dropped).
- **Types**: `Source<T, P, E>`, `Path`, `View<P, E>`, `Component<P, Pd, E>`, `TypedProps<P, "Key">`, `PropColors`, `RowBlock`, `EventHandler`, and the op types (`Read`, `Wait`, `Raise`, `Write`, `Create`, …).

### The userland route

Every operation a block delegates to with `yield*` runs inside its own iterator and returns without yielding, so `yield* count` is a plain tracked call in whatever computation is running the block. The only operation that yields to a driver is an async `attempt`: the `$memo` / `$event` runner suspends the generator on the promise and resumes it (a memo's compute returns the resumption's promise, so Solid's own async handling applies). A view generator, after the transform's rule, has no `yield` left and runs once; each hole is its own computation. Which block is running (its host, an effect's cleanups, a memo resumed after its attempt, a view's top level, a JSX-position read) is one value the runtime replaces whole for each run (`runAs`) and restores after, so a run started inside another — a view built while a memo resumes, a child's setup in a parent's view — starts from its own state (runtime "host state is per run (re-entrancy)").

What the runtime uses from Solid, all public exports: `action`, `createMemo`, `createRenderEffect`, `createSignal`, `createStore`, `createTrackedEffect`, `getObserver`, `getOwner`, `isPending`, `latest`, `onCleanup`, `onSettled`, `runWithOwner`, `untrack`, `useContext`, `createContext`, the flow controls, and `@solidjs/web`'s `render` / `hydrate` (plus `@solidjs/h` for the no-JSX flavor). The one lower-level hook is **`getObserver()`**: the runtime tells a view's own top-level read (no observer: `READ_IN_VIEW`) from a hole's (the hole's computation), and a setup's read from the first pass of a plain Solid computation the setup created. Since whole-view reads are gone (D-032) both uses are development checks (`READ_IN_VIEW`, `READ_IN_SETUP`): production never calls it. No private API, no patched core.

Two detections the userland route needs where a compiler would know statically:

- **A view that reads at its top level** is a development error when the read happens (`READ_IN_VIEW`, naming the component or row; on the server too). There is no whole-view re-render: a view runs once, and production builds do not check. Reads through `perform` — JSX positions — are never attributed to the view or setup on the stack, even when plain Solid code performs them untracked right then (a `<Reveal>` reading its `order` getter while a nested card's view is built). TypeScript cannot hold a JSX view to this: it types a `yield*` in JSX (a hole, after the transform) and one in a statement alike, and the former is how a JSX view's coloring is its holes'; a no-JSX view yields nothing, so there the type does (`[HVIEW_READ]`).
- **Row blocks** are recognized at runtime: a render callback that is a generator function runs its setup and view per row; a function marked as a view (a lazy page's output) is content, not a callback.

## 4. Lint rules (`@solidjs/eslint-plugin-blocks`, flat config, `recommended` = all errors)

| Rule                   | What TypeScript cannot say                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `no-throw`             | a block raises typed failures with `yield* raise(error)`, never `throw` (a `throw` is invisible to the failure types)     |
| `no-read-in-view-body` | a JSX view has no body (D-032; an `h` view — no JSX in its body — is the type's, `[HVIEW_READ]`, D-049): a `yield*` in a view that is not in a JSX expression / attribute (nor in a bare `function*` hole, whose reads are its own) — a read, a branch on one, a top-level `yield* Child(…)`. Views are recognized as a setup's or a row's returned `function*` (also a conditional return); rows also in the call form (`children:` / `fallback:`) and bound to a `const` in a setup |
| `yield-in-jsx-hole`    | every `yield*` in JSX is in a position the transform makes a hole; reports exactly the transform's refusals               |
| `read-before-attempt`  | a `$memo` reads before its first `attempt` (after an async attempt it resumes outside tracking)                           |
| `no-unyielded-write`   | a block setter writes only when delegated to (`yield* setX(v)`): a bare call writes nothing and is invisible to the types |
| `no-foreign-reactive`  | block code imports no reactive state the library did not create (Solid's primitives, the router's hooks, `dynamic`)       |
| `typed-props-key`      | an exported `$component` names its linker key (`TypedProps<P, "Name">`); autofix                                          |
| `no-path-object-use`   | a path (a setup's `props.x…`, a `$store` / `$optimisticStore` / `$projection` binding or a key of one, a row's argument) is a read, not an object: spreading it, `===` / `!==` on it, or `JSON.stringify` of it never sees the data — use `yield* path`. Syntactic: paths passed through helpers or stored elsewhere are not followed |
| `no-dollar-block`      | `$` / `$scope` are removed (D-013); autofix: a no-JSX hole becomes the bare `function*`, a row the bare `function*`, a derivation bound in a setup or a row's setup `yield* $memo(…)` (importing `$memo`); a module-level source or a JSX child is reported without a fix. Kept to report any remaining use |

Every twin lints `src` (the rendering twin `shared/src`) with the recommended set plus `@typescript-eslint/no-explicit-any`.

## 5. The JSX transform's rule

One syntactic rule, in the native compiler (`packages/compiler/src/blocks_rule.rs`) and `@solidjs/babel-plugin`: inside a JSX expression container or attribute value, `yield* e` becomes `perform(e)`, imported from the configured `blocksModule` (default `@solidjs/blocks`). The read becomes its own hole, and the view generator runs once. Refused (a compile error with a code): an event prop (`BLOCKS_YIELD_IN_EVENT`), `ref` (`BLOCKS_YIELD_IN_REF`), a spread attribute (`BLOCKS_YIELD_IN_SPREAD`), a spread child (`BLOCKS_YIELD_IN_SPREAD_CHILD`), and a plain `yield` (`BLOCKS_PLAIN_YIELD_IN_JSX`). The list is `packages/compiler/tests/blocks-rule-fixtures.json` (versioned), shared by the Rust tests, the Babel tests and the lint rule's parity test.

## 6. The type linker

TypeScript sees one component at a time: a child declaring `TypedProps<{ user: User }>` cannot know that a parent passes an async memo. The linker closes that gap with facts from every render site.

**Analysis** (`summarizeBlocks(code, { filename })` in `@solidjs/compiler`, Rust, `src/blocks_summary.rs`): one module in, one JSON document out, never rewriting code.

**Schema `solid-blocks-summary`, version 1** (`BlocksSummary` in `packages/compiler/types.d.ts`):

| Field                               | Content                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `schema`, `version`                 | `"solid-blocks-summary"`, `1` — consumers check both                                                                                                               |
| `imports` / `exports` / `reexports` | the module's edges and names                                                                                                                                       |
| `statics`                           | module-level `const`s bound to literals                                                                                                                            |
| `classes`                           | module-level classes (raised error types the linker can name)                                                                                                      |
| `components[]`                      | every module-level `$component`: `local`, linker `key` (from `TypedProps<P, "Key">`), `propsParam`, the value fact of each setup binding, `span`                   |
| `renders[]`                         | every render site of a capitalized component: `form` (`tag` / `call` / `h`), `owner` component, `inLoading` / `inErrored`, `spread`, a value fact per prop, `span` |
| `escapes[]`                         | components used as values (`<Dynamic>`, stored, passed): callers unknown                                                                                           |

Value facts, "may" facts joined over every known render site: `static`, `value` (read by the caller: settled for the callee), `live` (signal, store path, row item), `memo { pending, fails[], reads[] }` (pending when its body attempts or returns a promise / async iterable; fails with what it raises or declares), `prop { name }` (pass-through: the caller's callers' facts), `unknown` (the declared type, widest).

**Solve and emit** (`@solidjs/blocks-linker`): summaries cached by content hash; imports resolved (relative, and the project's tsconfig `paths` aliases); facts joined per component and prop to a fixpoint through pass-throughs; components whose callers are not all visible (used as values, `<Dynamic>`, exported from public modules) stay **open** and keep their declared types. Output: a committed declaration file (`src/solid-props.gen.d.ts`) merging `PropColors[Key][prop] = { pending; fails; live; static }`, which `TypedProps` reads. The Vite plugin updates it on save in dev (about 2.6 ms for a 63-module project) and fails `vite build` when it is stale; `solid-link --check` does the same in CI. Every twin commits its output and checks it.

**How the experiment branch's summarizers map onto it.** The `experiment/iterable-signals` branch (blocks v2 with a compiler) has five per-module summaries. Each is a question a whole-graph linker asks; v1 answers the one types need and has room for the rest:

## 7. Limitations (without the blocks compiler)

- **No islands.** Hydration is Solid's: every hydrated component runs. Island boundaries need per-handler reads / writes (see the table) and a compiler to split chunks.
- **No server components** (D-058). The blocks model has none: the idea is that a future compiler finds inert regions and turns them into server components itself. Server *data* (server functions, SSR) is supported; the twins whose point was server components (chat, hackernews, notes) were removed, and room's twin keeps only its live-server-function page.
- **No runtime tiers.** The app ships the full runtime plus the interpreter; selecting a sync-only or smaller runtime needs a whole-graph capability proof and a compiler to lower blocks.
- **Interpretation cost** (section 8): generator objects per setup / view / row, proxy paths for props and stores, one `perform` call per hole.
- **An effect cannot trigger an async event** (D-035, `start()` removed): an `$effect` delegates only to a synchronous event; work that must wait is modelled as an event calling an event, or as a `$memo`.
- **Failures with no boundary are re-thrown**: typed failures are complete for library-mediated failures; a plain throw is a bug surfaced in development (`UNTYPED_THROW`); either routes to the nearest `Errored` if there is one, otherwise it is re-thrown (D-033). The types still require a boundary wherever a failure meets a position that takes only settled elements (a tag, a row's view, the root of `render`) — see DECISIONS' open question on D-044.
- **Detections at run time**, not compile time: a JSX view's top-level read is found when it happens (`READ_IN_VIEW` in development, and a lint rule), not by its type; a row block is recognized by its function kind.
- **No plain Solid at the edges**: reactive state from plain Solid, the router or another library cannot enter block code (`no-foreign-reactive`); integrations are rewritten as block code (the twins: the todos data layer, the Effect saga driver, the notes search field). What crosses a server border keeps a stated coloring: two casts, each commented (chat's usage stream never rejects; a streamed row reads an index the store already holds); the router cannot see a route's coloring (the twins' `route()` states it); the library's `render` takes a settled root, so an app whose root is pending by design (the rendering example) mounts through `@solidjs/web` and is not checked there.
- **Paths are proxies**: a path answers only reads (`yield*`), keys (a longer path), `toString` / `toJSON` / `Symbol.toPrimitive` (its description) and `then` (`undefined`, so it is never taken for a promise). A data key with one of those names cannot be read through a path (read the parent and take the key from the value). Listing a path's keys, asking for a descriptor, defining or deleting a key is a dev error (`PATH_OBJECT`); production shows no keys and refuses the change.
- **Types are per component plus linker facts**: helper generators are opaque to the linker; open components keep their declared types.

## 8. Runtime cost: uncompiled blocks vs handwritten Solid on `next`

`examples/blocks-harness/runtime-cost/measure.mjs`: each workload written twice (handwritten Solid; `@solidjs/blocks` run by its interpreter with only the JSX transform's rule), bundled for production with the native compiler, mounted in jsdom, run under Valgrind cachegrind (no cache simulation) with `node --jitless`. Per operation: the instruction count of R operations minus the same process doing none, divided by R. `--wall` adds JIT-enabled wall time (median of five runs of 200 operations).

Measured on this branch (10 operations per count; wall: JIT on, 200 operations, median of 5):

| workload                          | handwritten Solid (instructions / op) | `@solidjs/blocks`, uncompiled | ratio |               difference / op | wall, Solid / blocks (ms / op) |
| --------------------------------- | ------------------------------------: | ----------------------------: | ----: | ----------------------------: | -----------------------------: |
| todos: add a todo, then toggle it |                             4,097,720 |                     4,525,976 | 1.10x |                         +428k |                    1.09 / 0.95 |
| 1,000 rows: create, then clear    |                         1,505,358,498 |                 1,574,854,638 | 1.05x |        +69.5M (≈ 69k per row) |                    87.2 / 93.1 |
| 1,000 rows: update every 10th     |                            14,960,308 |                    18,323,066 | 1.22x | +3.4M (≈ 34k per updated row) |                    0.72 / 0.80 |

Reading them: creation pays for a generator object per setup and view, per row, plus proxy paths; an update pays for the path read through the proxy and `perform` in each hole that re-runs. JIT wall times move with the same sign except the todos case, where the difference is within run-to-run noise on this shared machine (instruction counts are the figure to compare).

What the numbers include: everything each operation does, jsdom's DOM work included (the same for both flavors, and the larger part of each count), so the ratio understates the interpreter's share of the framework's own work; the absolute difference is the interpreter's cost per operation.
