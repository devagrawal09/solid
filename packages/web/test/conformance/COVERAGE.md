## Declared differences, defects and exclusions

- **≠ declared: `$` closes a superseded/disposed run's generator at its pending `wait`; an async function continues after `await` (its result is discarded)**
  - async-flights (client/runtime), async-flights (client/compiled), async-flights (client/fused), async-disposal (client/runtime), async-disposal (client/compiled), async-disposal (client/fused)
- **≠ declared: documented limit of the uncompiled driver (generator.ts module notes): props are plain getters, not proxies, so `yield* props.label` without lowering runs the getter's signal read under the strict guard and fails loudly with [DIRECT_READ_IN_BLOCK]**
  - prop-paths (client/runtime)
- **≠ declared: the same documented limit on the server: the server runtime has no strict read guard, so uncompiled `yield* props.label` delegates to the prop's string value and the driver refuses the yielded characters**
  - prop-paths (server/runtime)
- **n/a: server/runtime cannot render this scenario (see its declared difference)**
  - prop-paths (hydrate/runtime)
- **≠ declared: JSX `yield*` is a compiler-only spelling (generators-fixtures.test.js: a JSX yield is not a usable program without the pass): uncompiled, the child read is taken once per block run, so the whole block re-executes instead of a fine-grained insert**
  - jsx-block (client/runtime)
- **≠ declared: without the generator compiler, the server driver reads the accessor correctly but no creation-anchored blockScope is emitted; the deferred block therefore claims its element ID after its siblings**
  - jsx-block (server/runtime)
- **≠ declared: blockScope reserves the block's source-order slot and allocates its JSX in that child namespace; the IDs intentionally differ from an ordinary component while matching the hydrating client**
  - jsx-block (server/compiled), jsx-block (server/fused)
- **n/a: generators:false deliberately omits the compiler-emitted blockScope, so server/runtime's deferred ID layout has no matching hydration scope**
  - jsx-block (hydrate/runtime)
- **≠ declared: hydration preserves the server's scoped block ID namespace, so the keyed HTML differs from an ordinary component while node reuse, reads and updates remain equivalent**
  - jsx-block (hydrate/compiled), jsx-block (hydrate/fused)
- **≠ declared: Markup only: Solid's compiled template inserts a `<!---->` marker between adjacent text expressions; @solidjs/h appends text nodes without one. Every read, write and run is identical (the uncompiled view is one computation, so both reads of `count` re-run together, as in the compiled output here).**
  - blocks-counter (client/blocks-uncompiled)
- **≠ declared: Uncompiled `$effect` runs as one tracked pass (no split): on a re-run the previous cleanup runs before the new reads (not after), the branch read of `c` happens inside the effect body after the write of `b`, and the first run reads after the view's first render. Same subscriptions, values, runs and cleanups; different ordering.**
  - blocks-effect (client/blocks-uncompiled)
- **≠ declared: Uncompiled granularity: the parent view is one computation (a generic JSX transform cannot make each `yield*` its own effect), so its first read happens before the child is created and a write of `other` re-runs the whole parent view, which re-creates `Child` (its setup runs again). The child's own prop read stays fine-grained. Follow-up: reconcile component calls by position across view re-runs.**
  - blocks-props-child (client/blocks-uncompiled)
- **≠ declared: Uncompiled pipeline only (generic JSX transform + @solidjs/h): the known child re-creation. `<Saver />` under the context provider is an h thunk; the provider resolves its children with `flatten`, which calls the thunk and renders the returned view in the same computation, so the view's read of `saved` subscribes that computation. The resumed write re-runs it, the thunk re-creates `Saver` and the fresh instance reads `none`. Needs position-based reconciliation of component calls in uncompiled views (open); compiled output creates the component outside the resolving computation and matches the oracle.**
  - blocks-async-event (client/blocks-uncompiled)
- **n/a: Hole order is the subject here, and the uncompiled view is one computation (every hole re-runs together, in view order), so it has no per-hole order to compare.**
  - tier-two-cells (client/blocks-uncompiled)

## Semantic areas

- **memo-effect-order**: initial values; rerun order; equality suppression; memo/effect scheduling
- **dynamic-subscriptions**: unconditional subscriptions; branch-sensitive subscriptions; unsubscribe / resubscribe
- **owned-children**: cleanup on recomputation; child-owner disposal across recomputation; nested computations; disposal order
- **owner-routing**: owner identity; context through owners; untrack keeps the owner
- **error-routing**: synchronous throw; typed failure (raise); untyped failure (attempt); local recovery (try/catch); error-boundary routing and reset
- **async-flights**: async pending; async resolve; superseded stale flight; async reject → boundary; continuation ownership; loading/error markers
- **async-disposal**: disposal before settlement; no commit after disposal
- **event-reads-writes**: event reads are one-shot; event writes occur once; event handler owner
- **async-event**: async event pending/resolve; async event reject → boundary of the creating owner; writes before and after an event wait
- **store-paths**: store property paths; store index paths; array length; structural selector (readStore); unrelated store writes do not rerun
- **store-dynamic-index**: dynamic index key; index resubscription
- **prop-paths**: prop paths; prop subscriptions through getters
- **jsx-block**: JSX block returned from a component; fine-grained JSX reads; hydration-ID parity
- **async-hydration**: SSR async resolve + Loading markers; hydration reuses serialized async results (no duplicate authoritative work); post-hydration async update
- **error-markers**: SSR error-boundary fallback; hydrating an errored boundary; reset after hydration
- **blocks-counter**: component setup runs once; memo in setup; view reads; event reads and writes
- **blocks-effect**: effect reads and writes; effect cleanup per run and on dispose; branch reads in an effect; effect split (compute / effect halves)
- **blocks-props-child**: props forwarded as a source; child setup runs once; parent re-render does not re-create the child
- **blocks-async-resolve**: async memo under Loading; Loading / Errored call forms; boundary nesting
- **blocks-async-reject**: async failure reaches Errored through Loading; typed failure
- **blocks-context**: yield* Ctx in setup
- **blocks-async-event**: event that waits (`yield* attempt(() => promise)`); write after the wait; context read through a helper generator
- **tier-toggle**: tier 0: one cell written only by its own handler; holes read unconditionally (class, text, style); writes batched until the flush; a toggled-back batch still recomputes the holes
- **tier-two-cells**: tier 0: two cells, holes reading one or both; hole order after a batch: first-written cell's holes first, each hole once; handler reads see the committed value; equal writes are no-ops
- **tier-shared**: tier 1: a cell shared by two islands through props; memo over the shared cell; a branch over the memo (dynamic structure), cleanup when it closes
- **tier-diamond**: glitch-free diamond (each memo and effect once per batch); render effects before user effects; effect cleanups before the next run; a batch that returns to the committed value

## Planned modes (not implementable at this baseline)

- `client/strict` — non-generator strict frontend: no strict source frontend or `mode: "strict"` compiler option exists yet
- `client/proxy-free-stores` — proxy-free store lowering: stores are always proxies; no compiler/runtime option selects another representation
- `client/cold-events` — cold event-domain extraction: proposal only (typed-generator-compiler.md, App Bundle Prototype Priorities)
- `hydrate/runtime-selected` — runtime-selected / resumable hydration: hydration always re-executes the component tree; no selection manifest exists
- `server/server-components` — server components: harness gap, not a platform gap: the compiler's `serverComponents` option and @solidjs/web frames exist, but running a scenario as a server-component tree needs a frame-streaming runner and client-reference boundaries this harness does not implement yet
